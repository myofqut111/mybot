# 自主探索 · 打滑与低矮障碍 修复方案

> 版本：1.1（§5 改为"短墙 + 禁试区"） ｜ 日期：2026-11-16 ｜ 适用：`mybot_explore` 0.2.7 / `mybot_navigation` 0.1.2
> 状态：**待批准**（批准后按第 9 节顺序施工）

---

## 1. 问题是什么

### 1.1 现场现象

车往一个"雷达看不见但车过不去"的地方开（桌面下、架子横梁下、桌腿之间）：

1. 车顶到障碍物，轮子打滑，**车原地不动**
2. `/odom` 照常累加（轮式里程计测的是轮子转了几圈，不是实际位移）
3. nav2 只信 `odom` + 地图，**认为已经到了**
4. `navigate_to_pose` 报成功（status 4）
5. slam_toolbox 拿这个错误位姿继续拼接新扫描
6. 地图撕裂：同一面墙出现两层，边缘一片放射状拖尾

### 1.2 图上的证据

用户 2026-11-16 19:46 探索后自动存下的 `explore_20261116_1946`：

| 指标 | 这张图 | 参考（正常图 `map_newst`） |
|---|---|---|
| 尺寸 | 229 × 282 @ 0.05 m | 235 × 236 @ 0.05 m |
| 未知 | 52.0% | 53.6% |
| 空闲 | 45.5% | 42.1% |
| 障碍 | 2.5% | 4.3% |
| **孤立障碍率** | **16.90%** | 7.76% |
| 去毛刺后 | 9.64% | 4.26% |

形态上：房间轮廓被拉长，**中间出现一条弧形深色线**（同一面墙在两个位姿下各记一次，重叠成两层），边缘有放射状白色条纹（打滑期间的扫描被"推"出去）。

### 1.3 因果链

```
激光扫的是 Z≈15 cm 那个平面
    ↓ 桌子下面的空隙扫过去是空的
地图写成"可通行"
    ↓ 规划器正常规划穿过去
轮子撞到桌腿/横梁
    ↓ 打滑，车不动
/odom 继续累加（假位移）
    ↓ nav2 只信 odom+map
导航报 SUCCEEDED
    ↓ slam 用错误位姿拼接
地图撕裂
```

**根本矛盾**：`/odom` 会撒谎，2D 激光又看不见这个障碍，两个传感器都没有报错，系统就认为一切正常。

## 2. 目标与非目标

### 目标

1. **能识别**"命令在走、odom 在涨、但车实际没动"
2. **识别后立刻止住**：不让假位姿继续污染地图
3. **把那片区域记成"障碍"而不是"未知"**（本来也过不去）
4. **当场让规划绕开**，不让车反复往里试

### 非目标（明确不做）

- 不做视觉/深度相机补盲（要硬件）
- 不做真正的 3D 障碍建模
- 不改 `slam_toolbox` 内部算法
- 不做"事后修图"（把已经撕坏的图修回去，难度等同重做回环检测）

---

## 3. 核心思路：两个判据，必须同时成立

### 3.1 为什么不用"点云坐标直接比"

用户的想法（有效运动时 odom 和点云都变，打滑时只有 odom 变）方向正确，但"点云坐标"不能直接比：

| 情况 | 现象 | 直接比的后果 |
|---|---|---|
| 原地转向 | 所有点都变 | 误判成"在动"（其实正常，不该报） |
| 直线前进 5 cm | 近处点变多、远处几乎不变 | 阈值极难设 |
| 空旷区 | 大量光束打空 | 没有可比点 |

所以不能比"点变了没"，要**按运动类型分类**，并换一个更稳的量。

### 3.2 判据 A：`map→odom` 在长（主判据）

`slam_toolbox` 一直在算两件事：

- odom 说车在哪（`odom→base_link`）
- 激光匹配认为车在哪（`map→base_link`）

两者的差就是 `map→odom`。**这个差恰好等于"odom 累积了多少假位移"**：

```
正常行驶：odom 说走 1 m，匹配也说走 1 m → map→odom 几乎不变
打滑时：  odom 说走 1 m，匹配说没动      → map→odom 往反方向长 1 m
```

**优点**：免费（SLAM 每秒都在算）、比两帧点云稳（基于累积多帧）、不用自己写匹配算法。

**采样**：每秒读一次 TF `map→odom` 的平移分量，记录 3 秒滑动窗口内的累计变化量。

### 3.3 判据 B：扫描没变、odom 在涨（确认判据）

```
取相邻两帧 /scan，只统计 3 m 内命中的光束
统计 |r_i(t) − r_i(t−1)| > 0.03 m 的束占比
占比 < 15%  →  "扫描认为车没动"
同时 odom 位移 ≥ 0.10 m → "odom 认为车动了"
```

### 3.4 判定规则

```
slip = A 和 B 同时成立，且满足下面三条排除条件
```

**排除条件**（避免误报）：

| 条件 | 阈值 | 理由 |
|---|---|---|
| 角速度过大 | `|ω| > 0.3 rad/s` | 原地转圈时点云本来就该大变 |
| 有效束太少 | 3 m 内命中 < 40% | 空旷区没有可比性 |
| 命令速度≈0 | `|v| < 0.05 m/s` | 车本来就该静止 |

## 4. 判定之后做什么

### 4.1 动作序列

```
1. 取消当前导航目标（cancel NavigateToPose）
2. 调 /slam_toolbox/pause        ← 止住污染，最关键的一步
3. 在 (x, y) 记一个"挡住点"
4. 该点拉黑（半径 0.8 m），换下一个目标
5. 车真动起来（判据 B 显示扫描开始变化）→ /slam_toolbox/resume
6. 日志：疑似低矮障碍：车在 (x,y) 打滑 3.2 秒，已暂停建图并绕开
```

### 4.2 为什么"暂停建图"比"事后修图"划算

事后修图要判断"哪一段扫描是坏的"，等于再做一次回环检测，很难做对。
**在打滑发生的那一刻暂停**，坏数据根本进不了地图，代价只是那一小片留空——而那片随后会被标成障碍（见第 5 节）。

### 4.3 状态机

```
NAVIGATE ──(slip)──> SLIP_HOLD ──(真移动)──> SELECT
                        │
                        └──(超时 10 s 还没动)──> 放弃本点，回 SELECT（保持 pause）
```

`SLIP_HOLD` 期间不发新目标，只监测是否真的动起来。

## 5. 挡住点：只标有物证的部分

### 5.1 车只知道一件事

打滑那一刻，车掌握的确凿信息只有一条：

> **"我在 P 点、朝 H 方向，车头撞到了东西。"**

它不知道那是一个桌子腿、一整张桌子，还是一堵墙。**所以只能标"这句话蕴含的最小事实"，不能多标。**

### 5.2 标法：一条"车头宽的短墙"

```
        朝向 H
          ↑
   ───────┼───────   ← 垂直于车头的一段墙，长 0.5 m
          │
        [ 车 ]        ← 墙在前保险杠位置（车身前沿 + 2 cm）
```

| 属性 | 取值 | 依据 |
|---|---|---|
| 位置 | `pose + 0.22 m × 朝向` | 车头前沿在哪 |
| 方向 | 垂直于车头朝向 | 车只能正着撞 |
| 长度 | **0.5 m**（车宽 0.3 m + 两侧各 0.1 m 余量） | 车头这一截确实撞上了 |

**0.5 m 的依据是车自己的宽度，不是猜的**——这一截宽度内必有东西。超出这一截的部分，车没有证据，一律不标。

### 5.3 其余部分保持未知（灰）

| 区域 | 状态 | 含义 |
|---|---|---|
| 短墙那 0.5 m | 障碍（黑） | 车头撞到过，有物证 |
| 桌子底下那片 | **未知（灰）** | 车没走到，不知道 |
| 墙两侧 | 不变 | 没证据 |

灰色在这里的含义是"车没有走到"，不是"这里能走"。**留着灰洞比编造一片黑墙诚实。**

### 5.4 防止反复往里试：禁试区（不写进地图）

如果不处理，探索会发现"那片还是未知"，于是又往那儿选点，再撞一次。

单独记一份**禁试区**（`~/.ros/mybot_blocked.json`）：

```json
{
  "version": 1,
  "spots": [
    {"x": 3.42, "y": -1.05, "heading": 1.57,
     "hits": 2, "slip_seconds": 3.2,
     "first_seen": "2026-11-16T19:46:12", "last_seen": "2026-11-16T19:52:03"}
  ]
}
```

- 半径 `keepout_radius_m = 1.0 m`，里面不再选前沿点
- **只在选点用，不写进地图**
- 随时能删、能手工改

### 5.5 为什么不多标：两种错误代价不对等

| 标错方向 | 后果 | 能挽回吗 |
|---|---|---|
| **多标**（把能走的地方封了） | 那片区域永久进不去，覆盖率下降 | ❌ 很难 |
| **少标**（该封的没封） | 车再试一次，再撞一次，然后拉黑 | ✅ 只浪费 10 秒 |

**多标是永久损失，少标是暂时浪费 → 宁可少标。**

### 5.6 渐进策略（第 3 次才探测）

不搞"一次打滑就大动干戈"，按次数升级：

| 第几次 | 动作 |
|---|---|
| 第 1 次打滑 | 短墙 0.5 m + 禁试区 |
| 同一片第 2 次打滑 | 禁试区扩大（墙**不变长**，仍无证据） |
| 同一位置被第 3 次重新探索到 | 这时才值得做一次主动探测（P0 不做，只留接口） |

第 3 次才探测的理由：那时说明"从别的角度也绕不过去"，这片确实是死角，花 30 秒测一次才划算。

**P0 阶段的结论：不做探测。** 大多数情况下，车会从别的角度靠近那片区域，激光从侧面一扫，真实轮廓自己就画进地图了——"等下一次从别的方向看见"比"专门跑过去摸一遍"更划算，也没有额外风险。

### 5.7 可追溯

三样东西分得清楚：

| 文件 | 内容 | 谁产生的 |
|---|---|---|
| `xxx.pgm` / `xxx.yaml` | 原始地图（只有激光测到的东西） | slam_toolbox |
| `xxx_clean.pgm` | 去毛刺版（清孤立噪点） | 我们 |
| `xxx_blocked.json` | 推断出的短墙与禁试区（**人工推断**） | 我们 |

文档和 README 里写明：**`_clean` 版含推断成分；要严格的原始数据用 `xxx.pgm`。**

## 6. 顺带修：导航虚报成功

nav2 报成功，本质是"odom 认为到了"。加一条**到达校验**：

```
到达前后各取一帧扫描（距目标 ≤ 0.5 m 与到达瞬间）
若变化束占比 < 15% → 车其实没挪窝 → 判失败，不发"到了"
```

和判据 B 共用同一套扫描比对代码，多写约 20 行。

## 10. 验证计划

### 单测（不依赖 ROS）

- 正常行驶（odom 涨、扫描变）→ 不报
- 原地转（ω 大）→ 不报
- 空旷（有效束少）→ 不报
- **打滑**（odom 涨、扫描不变）→ 报
- 打滑 1.4 s 不确认、1.6 s 确认
- 挡住点：同一位置两次 → 持久化；一次 → 只拉黑
- 盖章：半径内格子变障碍，半径外不动

### mock（不依赖真车）

写一个"假打滑底盘"：收 `cmd_vel` 但位姿走到障碍前就不动了，odom 照常累加。
跑一轮，检查：是否 pause、是否记录挡住点、地图里那点是否变黑。

### 真机（最终验收）

推到"桌子下面"那种地方，看：

1. 打滑后 2 秒内取消目标
2. 日志出现 `疑似低矮障碍`
3. slam 暂停（`/slam_toolbox/pause` 被调用）
4. 换目标继续跑，不再尝试那个位置
5. 收工时存下的图里，那片是黑的

## 11. 风险与回退

| 风险 | 概率 | 对策 |
|---|---|---|
| 误报（正常行驶被判打滑） | 中 | 两个判据必须同时成立 + 三条排除；日志打印两个判据的原始数值，便于调阈值 |
| slam 的 `map→odom` 不刷新（静止时不处理扫描） | 中 | 判据 B 独立成立即可动作；A 只作加权 |
| 暂停后忘记恢复，地图永远不更新 | 中 | `SLIP_HOLD` 有 10 s 超时；`/explore/status` 增加 `slam_paused` 字段可查 |
| 挡住点盖错地方（临时障碍） | 中 | 连续 2 次才持久化；`blocked.json` 可手工编辑 |
| costmap 新增观测源导致规划异常 | 低 | 参数化，`blocked_publish` 关闭即恢复原状 |

**回退**：所有新功能都有独立开关（`slip_enabled` / `blocked_publish` / `goto_verify`），任何一个出问题单独关掉即可，不影响现有流程。

---

## 12. 验收标准

1. 真机上推出打滑后，**2 秒内**取消目标并暂停建图
2. 日志有一条 `疑似低矮障碍：车在 (x,y) 打滑 N 秒…`
3. 同一轮里不再尝试该位置（黑名单生效）
4. 收工存下的图里，打滑位置出现一条 **0.5 m 的短墙**（黑），其余仍为未知（灰）——不出现大片编造的黑区
5. 孤立障碍率不再出现 16% 这种量级（目标回到 8% 以下）
6. 全量单测通过（现有 82 + 新增 22 例）

## 13. 明确不做

- 加深度相机 / ToF 补盲（硬件，另议）
- 真正的 3D 建图
- 事后自动修图（把撕裂的图修回去）
- 多机协同探索
